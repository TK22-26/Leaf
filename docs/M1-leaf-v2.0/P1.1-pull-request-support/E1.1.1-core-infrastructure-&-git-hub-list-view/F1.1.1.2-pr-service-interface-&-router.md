# F1.1.1.2: PR Service Interface and Router

Define the application-facing pull request service contract and the provider-routing layer that sits behind it, including reviewer search capabilities.

## Deliverables
- `IPullRequestService` with repo-scoped methods for list, detail, create, update, merge, close, checkout, and find-by-commit.
- Reviewer-related methods: search reviewer candidates (users, teams, or groups as supported) and request reviewers on a PR.
- A router service that resolves provider capabilities from repository remotes.
- Provider adapter interfaces or internal abstractions to keep GitHub and Azure DevOps code isolated.

## Implementation Notes
- Prefer `IRepositorySession` at the service boundary for repository-scoped operations.
- Use `CredentialService` and current remote parsing conventions for auth and provider resolution.
- Avoid sync-over-async patterns such as `.GetAwaiter().GetResult()` when resolving remotes.
- Do not route refresh through custom PR events; mutation callers should use `IRepositoryEventHub`.
- Reviewer search method should accept a search term and return a list of `ReviewerInfo` models with reviewer kind metadata. GitHub should compose cached collaborators plus repository-team results and filter client-side; Azure DevOps should use server-side identity search and map both users and groups.

## Acceptance Criteria
- [ ] The service contract is sufficient for all planned PR flows including reviewer search and assignment.
- [ ] Provider resolution works from current repository remote information.
- [ ] No stale assumptions remain about device-flow auth or non-existent git helpers.
- [ ] The router supports GitHub first and leaves a clear path for Azure DevOps parity.
