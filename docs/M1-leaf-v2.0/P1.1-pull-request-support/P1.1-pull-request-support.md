# P1.1: Pull Request Support

Add pull request support to Leaf using the current repository tree for discovery and the main content area for PR creation and detail viewing.

## Scope
- Providers: GitHub first, Azure DevOps second.
- Tree section: `PULL REQUESTS` sits beside `LOCAL`, `REMOTE`, `WORKTREES`, and `TAGS` with count badge, "+" add button, and filter button.
- Detail flow: selecting a PR replaces the git graph in the main content area with a PR detail view.
- Create flow: "+" button or branch context menu opens an inline create form in the main content area.
- Create form fields: source branch, target branch, title, description, reviewers (autocomplete), draft toggle. Work items are out of scope.
- Actions: list, refresh, filter, inspect, create, update, merge, close, checkout, and find by commit.
- All management actions available both in-app and via persistent "Open in browser" link.

## Architectural Direction
- Extend current tree infrastructure instead of adding a panel-specific browsing experience.
- Main content area is a multi-mode surface: git graph (default), PR create form, or PR detail view. Only one visible at a time.
- Right-side repository panel hides when any PR mode is active.
- PR detail and create modes are blocked while merge/conflict or orphaned-conflict state is active; show an actionable toast and keep the current repository-state UI visible.
- Navigation back to graph: close/back button on PR views, Accept/Cancel on create form, selecting any branch/tag/worktree in the tree, or selecting a commit in the graph.
- Reuse PAT auth via `CredentialService`.
- Use `IRepositorySession` for repo-scoped operations and `IRepositoryEventHub` for refresh.
- Keep provider mapping behind a single facade with provider-specific adapters.
- Extend the existing notification stack into actionable toast notifications for success/info messages with clickable links/actions.
- Follow current manual composition in `MainWindow.xaml.cs`; do not add a DI framework.

## Goals
1. Keep PR navigation consistent with existing Leaf tree behavior.
2. Use the main content area for PR creation and detail viewing.
3. Never lock users to Leaf or browser — always provide both options.
4. Deliver GitHub first without blocking Azure DevOps parity.
5. Avoid stale assumptions such as OAuth device flow or custom graph refresh events.
6. Minimize churn in shared tree infrastructure while still making PRs feel native.

## Testing Requirements
- GitHub and Azure DevOps manual matrix for supported flows.
- Regression coverage for `BranchListView` interactions because PRs share that surface.
- Provider adapter unit tests around payload mapping, pagination, and capability checks.
- Content-area mode switching tested for clean transitions and state cleanup.
- Reviewer autocomplete tested for both providers.

## Exit Criteria
- [ ] PR tree section loads for supported remotes with count badge, add button, and filter button.
- [ ] PR detail view renders in the main content area (not a separate panel or right-side region).
- [ ] PR create form renders in the main content area with reviewer autocomplete for users/teams/groups as supported by the provider.
- [ ] Post-create actionable toast can open PR detail in Leaf or the browser.
- [ ] Mutations refresh via current event hub patterns.
- [ ] "Open in browser" always visible in PR detail header.
- [ ] GitHub support is complete.
- [ ] Azure DevOps support reaches planned parity.
