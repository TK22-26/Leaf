# F1.1.3.1: Create Pull Request Form

Legacy filename retained for continuity. The implementation is an inline form in the main content area, not a modal dialog.

## Deliverables
- `CreatePullRequestView` that renders in the main content area, replacing the git graph.
- `CreatePullRequestViewModel` with form state, validation, and submission logic.
- Form fields: source branch (dropdown with search), target branch (dropdown with search), title, description (multiline), reviewers (autocomplete search), draft toggle.
- Accept and Cancel buttons at the bottom of the form.
- Reviewer autocomplete field that searches users/teams/groups via `IPullRequestService` and displays matching `ReviewerInfo` results for selection. Supports multi-select.
- Actionable toast built on the existing notification stack for post-create feedback:
  - Clickable link to open the new PR detail in Leaf (switches main area to PR detail view).
  - "Open in browser" link to open the PR's web page.
  - Toast auto-dismisses or can be manually closed.
- Provider-aware validation and capability messaging.
- Create flow that refetches the PR list after success.

## Implementation Notes
- The form is a full view (not a dialog) occupying the main content area. The right-side repository panel hides while the form is active.
- Do not enter create mode while merge/conflict or orphaned-conflict state is active. Show an actionable toast and keep the repository-state UI visible instead.
- Pre-populate source branch from the launch context when possible (from branch context menu or current branch).
- Validate that the source branch has a usable remote/upstream before creating the PR.
- Branch dropdowns should support search/filter for repos with many branches.
- Reviewer autocomplete: on text input, call the provider's reviewer search method. For GitHub, this fetches collaborators for user reviewers and repository teams for team reviewers on first open, then filters the combined results client-side. For Azure DevOps, this uses server-side identity search for users and groups.
- Cache reviewer directory data briefly per repo to avoid repeated API calls during the same create session. GitHub may maintain separate collaborator and repository-team caches behind the same interface.
- Accept button creates the PR and assigns selected reviewers in a single flow.
- Cancel button returns to the git graph without creating anything.
- After successful creation: show the actionable toast and refresh the PR tree section.
- Work items are explicitly out of scope — do not include a work items field.

## Acceptance Criteria
- [ ] Form renders in the main content area with correct layout and field ordering.
- [ ] Source branch is pre-populated from context when launched from branch menu.
- [ ] Branch dropdowns support search/filter.
- [ ] Reviewer autocomplete returns matching users/teams/groups and supports multi-select.
- [ ] Required fields (source, target, title) are validated before submission.
- [ ] Draft creation is available only when the provider supports it.
- [ ] Accept creates the PR and assigns reviewers.
- [ ] Cancel returns to the git graph without side effects.
- [ ] On success, actionable toast appears with actions to open the PR in Leaf or in the browser.
- [ ] Attempting to open the form during merge/conflict or orphaned-conflict state shows an actionable toast and leaves the current resolution UI in place.
- [ ] PR tree section refreshes after successful creation.
